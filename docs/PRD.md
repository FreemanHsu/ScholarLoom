## 1. 产品摘要

ScholarLoom 是一个面向个人研究工作的 AI-native 论文阅读与知识沉淀系统。
它把论文发现、原文阅读、可信摘要、围绕论文的讨论、代码参考、知识图谱、
Wiki 式主题索引和全局 Agent 问答连接为一个持续演化的闭环：

```text
发现或导入论文
  → 获取并解析原始材料
  → 生成可追溯的 Paper Summary
  → 围绕论文和开源代码持续讨论
  → 从讨论中提炼可复用观点
  → 更新论文关系、概念、主题和问题索引
  → 全局 Agent 基于分层索引回答问题
  → 用已有知识和兴趣模型发现下一批论文
```

产品的差异不在于“可以和 PDF 聊天”，而在于每一次阅读和讨论都会成为可追溯、
可检索、可继续演化的个人研究知识，并能改善下一次检索、问答和论文发现。

## 2. Problem Statement

论文研究通常分散在 arXiv、PDF 阅读器、GitHub、聊天工具、笔记软件和搜索引擎中。
这些工具能解决局部问题，但无法形成可靠的长期记忆：

- 新论文发现依赖手工关注，难以同时覆盖重点实验室和不断变化的研究方向。
- 自动摘要经常脱离原文，难以判断某个结论来自哪里、是否遗漏适用条件。
- 围绕论文产生的高价值讨论停留在聊天历史里，没有稳定结构，也无法反哺知识库。
- 论文之间除了显式引用，还存在继承、借鉴、对比、同一探索路线等语义关系，
  这些关系通常依赖个人记忆。
- 当论文和对话数量增长后，无法把全部内容放入模型上下文；普通向量检索也容易
  混淆原文、作者主张、个人观点和 AI 推断。
- 论文对应的开源代码与论文内容分离，讨论方法细节时无法有效交叉验证。

用户需要的不是另一个论文收藏夹，而是一套具有可信信源、长期记忆、分层索引和
主动发现能力的个人研究系统。

## 3. 产品目标

### 3.1 核心目标

1. 让用户通过一个 arXiv 链接即可获得可阅读、可检索、可追溯的论文工作区。
2. 根据用户明确配置的来源和知识库中形成的兴趣方向，持续发现值得关注的新论文。
3. 为每篇论文生成带原文定位的结构化 Summary，并支持与原文对照阅读。
4. 支持围绕单篇论文及其开源代码进行持续对话，并保存完整历史。
5. 将 Summary 和讨论中的稳定观点提炼为结构化知识，而非仅保存聊天记录。
6. 同时维护显式引用关系和带证据、置信度的语义关系，形成可审查的知识图谱。
7. 建立领域 → 方向 → 概念/问题 → 论文/讨论的分层索引，支持大规模知识检索。
8. 提供一个全局 Agent 入口，以原文、摘要、历史讨论、代码和结构化知识为信源回答问题。

### 3.2 非目标

- 不以替代专业引用管理器或完整学术搜索引擎为第一目标。
- 不保证自动发现覆盖所有出版渠道或付费墙后的论文。
- 不把模型生成内容视为与论文原文同等级的事实来源。
- 不执行来源不明的论文配套代码；代码执行环境不属于首期范围。
- 不训练自有基础模型；优先采用可替换的模型与解析服务。

## 4. 产品原则

1. **原始材料优先**：PDF、论文元数据和代码是一级信源；Summary、讨论和综合均为派生内容。
2. **回答必须可追溯**：重要陈述应能定位到页码、章节、图表、代码文件或历史讨论。
3. **不同声音必须分层**：作者主张、论文证据、用户观点和 Agent 推断不能混为一谈。
4. **自动化不等于静默写入**：低风险的显式关系可以自动确认；解释性关系应带置信度和审核状态。
5. **知识是演化的**：摘要、关系、主题页和索引必须可重建、可版本化、可纠正。
6. **Markdown 是长期事实源**：搜索索引、向量库、图数据库和 UI 是可重新生成的派生视图。
7. **先缩小再展开**：全局问答先通过分层索引定位主题和候选材料，再读取细粒度证据。

### 4.1 已确认的 MVP 决策

- 第一版验证“单篇论文深度阅读闭环”，主动发现不阻塞首版交付。
- 系统为单用户、本地优先的浏览器产品。服务、PDF、代码和知识源均保存在 Mac mini。
- 用户通过能够私下连通 Mac mini 的笔记本访问；首期不暴露到公网。
- 应用只监听 Mac mini 的 loopback 地址，由 Tailscale Serve 提供 tailnet 内的私有 HTTPS 入口；不使用 Funnel，不监听公网或普通 LAN 接口。
- AI 工作全部通过 Codex CLI 执行，不在首期额外抽象另一套直接模型调用层。
- PDF、GitHub 代码、历史对话和个人知识均允许作为 Codex 云端模型上下文。
- 显式事实自动写入；解释性关系和从讨论提炼的长期知识由用户确认。
- Paper Summary 遵循仓库内版本化的 `paper-reading` Skill，默认产出中文技术精读。
- 论文明确给出的 GitHub 链接自动克隆；搜索推断出的仓库必须由用户确认后才能克隆。
- Agent 主动建议值得沉淀的 Takeaway/Insight，用户通过一键确认写入长期知识。
- MVP 入口 Agent 只检索 Paper Summary 和已确认知识；向 PDF、完整对话和代码下钻的
  检索流程在数据层级完成设计后另行定义。
- 入口 Agent 使用独立的已确认知识 FTS 投影；索引暂时落后时仍可回答，但必须提示
  “知识索引更新中”及最后成功更新时间。
- 外部 Markdown 编辑被保留并进入待确认的 reconciliation Proposal；与应用中写入竞争时
  才标记为冲突。未处理 30 天后从待处理队列归档，但永久保留且可重新打开。

## 5. 用户与核心场景

首期只有一个主要角色：知识库所有者。系统 Agent 是协作者，不是独立的内容权威。

### 场景 A：从 arXiv 链接导入论文

用户粘贴一个 arXiv abstract、PDF 或版本链接。系统识别 canonical arXiv ID，检查重复；
显式 `vN` 链接固定导入该版本，裸 ID 只在导入时解析一次最新版本，
下载允许获取的 PDF 和元数据，提取文本、章节、表格、图片及页面坐标，生成结构化
Summary。同时，系统查找可能的开源 GitHub 仓库；若确认匹配，则下载固定版本并建立
只读代码索引。处理完成后，用户进入论文工作区查看 Summary、可选打开原文并开始讨论。

### 场景 B：主动发现值得关注的论文

用户配置重点实验室、作者、arXiv 分类、关键词或主题。系统也可以从已有的概念、
主题、开放问题和阅读行为中形成候选兴趣信号。定时发现新论文，去重并给出推荐理由，
由用户决定忽略、稍后阅读或导入。

### 场景 C：阅读和讨论单篇论文

用户首先进入完整的 Paper Summary；需要核验时再打开 PDF 形成左右分栏。点击 Summary
中的引用可定位原文。用户以 Summary 为起点在该论文范围内提问，Agent 默认使用论文
原文、Summary、已有讨论和经过确认的配套代码回答，并显示所使用的信源。

### 场景 D：把讨论沉淀为知识

对话完整保存，但不会把每条消息都当作长期知识。系统从一次讨论中提出“值得沉淀的
Takeaway、Insight、问题、关系或概念”候选，保留来源消息和论文证据。确认后的 Takeaway
继续挂在该 Paper 下；可复用 Insight 更新 Concept、Topic、Question 或 Synthesis。
二者都会进入全局 Agent 可检索的知识索引。

### 场景 E：跨论文和全局问答

用户从知识库首页提出问题。MVP Agent 只检索 Paper Summary 和已确认的 Takeaway、
Insight 及其他长期知识，给出带来源和不确定性的回答。PDF 原文、完整历史讨论和代码
暂不进入入口 Agent 的检索范围；向下检索的层级与路由在完整数据层级确定后另行设计。

## 6. User Stories

### 6.1 论文进入系统

1. 作为用户，我希望粘贴任意常见形式的 arXiv 链接，以便系统自动识别同一篇论文。
2. 作为用户，我希望系统在下载前检查 arXiv ID、DOI 和标题，以免重复导入。
3. 作为用户，我希望看到下载、解析、摘要生成和索引的处理状态，以便判断是否需要等待或重试。
4. 作为用户，我希望失败步骤可以单独重试，以免重复执行整条流水线。
5. 作为用户，我希望系统保留论文版本信息，以便知道 Summary 对应哪个 arXiv 版本。
6. 作为用户，我希望保留原始 PDF，以便随时核对派生内容。
7. 作为用户，我希望系统提取正文、章节、公式、表格、图片及页面定位，以便回答不仅依赖纯文本。
8. 作为用户，我希望补充或纠正论文元数据，以便修复自动识别错误。

### 6.2 主动发现

9. 作为用户，我希望关注实验室、作者、arXiv 分类和关键词，以便持续获得新论文候选。
10. 作为用户，我希望用知识库中的 Topic、Concept 和 Question 作为发现条件，以便跟踪正在形成的研究方向。
11. 作为用户，我希望每个推荐都解释“为什么推荐给我”，以便快速判断相关性。
12. 作为用户，我希望候选论文先进入收件箱而不是自动污染知识库，以便控制阅读范围和成本。
13. 作为用户，我希望忽略、稍后阅读或导入候选论文，以便建立稳定的筛选流程。
14. 作为用户，我希望系统记住我对候选论文的操作，以便逐步改善推荐排序。
15. 作为用户，我希望系统合并来自不同发现源的同一篇论文，以免重复提醒。

### 6.3 Summary 与原文阅读

16. 作为用户，我希望每篇论文都有独立、长期可访问的 Summary，以便快速回顾。
17. 作为用户，我希望 Summary 覆盖问题、贡献、方法、数据、实验、结论、局限和开放问题，以便形成完整理解。
18. 作为用户，我希望 Summary 中的重要陈述带页码、章节、图或表定位，以便核验原文。
19. 作为用户，我希望系统明确标注只读到摘要、粗读或完整阅读，以便评估可信度。
20. 作为用户，我希望左侧查看 Summary、右侧查看 PDF，以便对照阅读。
21. 作为用户，我希望点击 Summary 引用时右侧 PDF 跳到对应位置，以便减少查找成本。
22. 作为用户，我希望 Summary 更新后保留历史版本，以便知道哪些认识发生了变化。
23. 作为用户，我希望添加自己的批注而不被 AI 静默改写，以便保留个人判断。

### 6.4 单篇论文对话与代码

24. 作为用户，我希望在论文工作区发起持续对话，以便深入理解论文。
25. 作为用户，我希望 Agent 默认限定在当前论文、其 Summary、历史对话和相关代码，以便减少无关答案。
26. 作为用户，我希望每个答案显示引用的原文、代码或历史讨论，以便核查信源。
27. 作为用户，我希望系统自动查找作者给出的官方代码链接，以便结合实现理解方法。
28. 作为用户，我希望系统区分官方仓库、作者仓库和第三方复现，以便判断代码权威性。
29. 作为用户，我希望代码引用定位到仓库版本、文件和行范围，以便复现回答依据。
30. 作为用户，我希望手动指定或排除代码仓库，以便纠正自动匹配结果。
31. 作为用户，我希望讨论历史按论文和会话组织，以便恢复此前上下文。
32. 作为用户，我希望在新会话中调用过去讨论的相关结论，而不必加载全部聊天记录。

### 6.5 知识沉淀与图谱

33. 作为用户，我希望系统自动提取论文参考文献关系，以便形成基础引用图谱。
34. 作为用户，我希望系统识别扩展、借鉴、对比、复现、反驳和同一研究路线等语义关系，以便理解领域演化。
35. 作为用户，我希望每条语义关系都有解释、证据、置信度和审核状态，以便控制错误传播。
36. 作为用户，我希望从 Summary 和讨论中提取 Concept、Topic、Question 和 Synthesis 候选，以便形成结构化知识。
37. 作为用户，我希望确认、编辑或拒绝提炼候选，以便知识库表达我的判断而不是模型的猜测。
38. 作为用户，我希望查看任意论文、概念或主题的上下游关系，以便探索知识图谱。
39. 作为用户，我希望新论文进入后自动提示可能受影响的旧观点和综合，以便持续更新认识。
40. 作为用户，我希望被替代的观点保留历史和替代关系，以便理解知识演进。

### 6.6 Wiki 与分层索引

41. 作为用户，我希望按领域、方向、主题、概念、问题和论文分层浏览，以便在大型知识库中定位内容。
42. 作为用户，我希望主题页自动汇总代表论文、关键概念、争议、开放问题和阅读路径，以便快速进入陌生方向。
43. 作为用户，我希望自动生成内容可以手工编辑且不会在重建时丢失，以便兼顾效率和控制。
44. 作为用户，我希望看到孤立论文、重复概念、失效链接和长期未更新的观点，以便维护知识质量。

### 6.7 全局 Agent

45. 作为用户，我希望在统一入口询问整个知识库，以便跨论文获得有针对性的回答。
46. 作为用户，我希望 MVP Agent 只检索 Paper Summary 和已确认知识，以便回答建立在已经整理的内容上。
47. 作为用户，我希望未确认候选、PDF 原文、完整对话和代码不被入口 Agent 静默检索，以便控制知识边界。
48. 作为用户，我希望回答区分共识、分歧、个人历史观点和 Agent 新推断，以便正确理解结论性质。
49. 作为用户，我希望查看回答实际使用了哪些材料以及为什么选择它们，以便评估检索质量。
50. 作为用户，我希望把高价值回答保存为 Question、Concept 或 Synthesis，以便反哺知识库。
51. 作为用户，我希望选择时间、主题、论文集合或信源类型作为查询范围，以便控制上下文。
52. 作为用户，我希望系统在证据不足时明确说不知道并建议下一步检索或阅读，以免得到虚假确定性。

## 7. 功能需求

### FR-1 论文采集与身份归一化

- 接受 arXiv abstract、PDF、HTML 和带版本号链接。
- 将链接归一化为 canonical arXiv ID，并保存版本号、抓取时间和原始 URL。
- 获取元数据、PDF 和可用的补充材料；不得绕过访问控制或付费墙。
- 以 arXiv ID、DOI、标题与作者组合进行幂等去重。
- 首期至少支持 arXiv；其他来源采用可扩展 Connector 接口。

### FR-2 异步处理流水线

- 论文处理状态至少包括：`candidate`、`queued`、`downloading`、`parsing`、
  `summarizing`、`indexing`、`ready`、`failed`。代码发现、下载和索引使用独立子状态，
  不与 Paper Ready 混成一个不可解释的总状态。
- 每个步骤记录输入版本、输出 Artifact、开始/结束时间和错误信息。
- 失败可从安全的最近检查点重试；重复任务不得生成重复 Paper。
- PDF、解析文本、多媒体、Summary 和索引均作为带版本的 Artifact 管理。

### FR-3 文档解析与证据锚点

- 按页面和章节提取文本，尽量保留阅读顺序和层级。
- 为文本块记录页码、字符范围和 PDF 坐标；图表记录 caption、页码和区域。
- 公式、表格和图片解析失败时保留原始区域，避免静默丢失。
- 所有下游 Summary 与回答引用统一的 Evidence Anchor。

### FR-4 Paper Summary

- Summary 生成必须执行版本化的 `paper-reading` Skill；该 Skill 是 Summary 内容结构、
  分析深度和表达风格的产品契约。
- 默认使用中文，保留标准英文技术术语，并面向具有 AI/ML 基础的读者进行详细技术精读。
- Summary 默认包含七个部分：Paper Overview、Core Ideas and Motivation、Technical
  Implementation、Training Process、Inference Process、Experiments Analysis、Summary
  and Thoughts。论文不涉及训练或推理时，按 Skill 规则省略完整章节并简述原因。
- 方法部分应解释输入、输出、组件、训练目标、推理路径和真正的创新位置；必要时使用
  公式、伪代码或短代码辅助理解。
- 实验部分必须把主要 claim 对应到主实验、消融或分析证据，并指出仅被作者声称而未
  得到充分验证的内容。
- Summary 应同时包含作者明确写出的局限和技术上有依据的独立评价，并明确区分二者。
- 每项重要结论至少关联一个 Evidence Anchor；无法定位时明确标记。
- 保存生成时间、模型、Prompt/策略版本、输入 Paper 版本和阅读深度。
- 用户笔记与模型生成 Summary 分区保存。
- 支持重新生成和版本对比；新版本不得覆盖用户批注。

### FR-5 论文工作区

- 进入 Paper 时默认展示完整 Summary；PDF 原文是可选打开的核验视图。
- 打开 PDF 后提供 Summary/PDF 左右分栏，并允许调整宽度和隐藏其中一栏。
- Summary 引用可以驱动 PDF 定位；PDF 选择内容可带定位地发起提问。
- 展示处理状态、论文元数据、版本、代码仓库和相关知识入口。
- 对话按 Paper 隔离，允许多个会话和历史恢复。

### FR-6 Paper-scoped Agent

- 默认检索范围为当前 Paper 的原文、Summary、用户批注、历史讨论和已确认代码。
- 回答必须返回所用证据；无足够证据时不得补造论文内容。
- 允许用户临时扩大范围到引用论文或整个知识库。
- 保存原始消息、回答、引用、模型信息和检索轨迹。
- 对长会话生成可版本化的会话摘要和候选 Insight，但保留原始消息作为最终追溯源。

### FR-7 代码仓库发现与索引

- 从论文正文、arXiv metadata、Papers with Code 类来源和 GitHub 搜索中发现候选仓库。
- 根据论文明确链接、作者身份、README 引用、标题和发布时间计算匹配置信度。
- 仓库必须标注 `official`、`author`、`third-party-reproduction` 或 `unknown`。
- 论文自身明确给出的 GitHub 链接直接自动克隆。
- 通过项目页、GitHub 搜索或其他外部来源推断出的仓库只能形成候选；用户确认前不得克隆或加入
  Paper-scoped Agent context。
- 对已确认匹配的 GitHub 仓库自动克隆到 Mac mini，记录固定 commit SHA，并建立只读索引；
  代码回答引用该版本的文件和行范围。
- 代码发现、克隆和索引与 Paper Summary 并行执行，不应因 GitHub 不存在或暂时失败而
  阻塞 Paper Summary。代码就绪状态必须在 Paper 工作区明确显示。
- 若代码在首版 Summary 完成后才就绪，可生成带版本的代码补充或 Summary 新版本，
  不静默修改用户已经读过的内容。
- 首期只读索引文档、配置和核心源码，不自动安装依赖或执行代码。

### FR-8 知识提炼

- Summary 完成和会话结束/达到阈值时触发提炼任务。
- `Takeaway` 是挂在单篇 Paper 下、可独立检索的精炼结论；`Insight` 是可能跨 Paper
  复用、进入结构化知识层的认识。两者都必须保存来源与确认状态。
- 提炼结果可以是 Paper Takeaway、Insight、Concept、Topic、Question、Synthesis 或
  Relation 候选。
- 每个候选保存来源 Artifact/消息、理由、置信度和审核状态。
- 用户可以接受、编辑、合并、拒绝；拒绝记录可作为未来推荐和提炼的弱反馈。
- 首版主交互是 Agent 主动展示非打断式候选，用户一键确认；主动保存命令可以保留为
  辅助入口，但不作为主要发现机制。
- 候选若展示为原文引语，系统必须在固定版本 PDF 页文本中重新匹配；无法验证时只显示
  未验证页级引用并要求用户先打开原文，不能一键确认。
- 显式 citation 可自动确认；解释性关系默认进入待审核状态。
- 全局 Agent 的 MVP 索引至少包含 Paper Summary、已确认 Takeaway、已确认 Insight 和
  它们的来源；完整知识图谱不是这条检索链路上线的前置条件。

### FR-9 知识图谱

- 节点首期包括 Paper、CodeRepository、Concept、Topic、Question 和 Synthesis。
- 边至少包括：`cites`、`extends`、`uses-method-from`、`compares-with`、
  `reproduces`、`contradicts`、`same-research-line`、`implements`、`about`、
  `supports`、`challenges`、`supersedes`。
- 每条边记录方向、来源、证据、创建者、置信度、审核状态和时间。
- 图数据库若被采用，只是 Markdown 事实源的派生视图；必须可全量重建。

### FR-10 Wiki 与层级索引

- 维护领域/方向/Topic/Concept/Question/Paper 的导航层级，但允许跨层和多归属关系。
- Topic 页面包含范围、概念地图、代表论文、学派/争议、开放问题、综合和推荐阅读路径。
- 系统生成区与用户编辑区需要明确边界，以防重建覆盖手工内容。
- 索引更新应增量执行，并提供全量重建与一致性检查。

### FR-11 MVP 入口 Agent

- 检索语料只包括 Paper Summary 和已确认的 Takeaway、Insight、Concept、Topic、Question、
  Synthesis 等长期知识。
- 未确认候选、PDF 原文块、完整历史会话和 GitHub 代码不进入 MVP 入口 Agent 的检索语料。
- 入口 Agent 只访问独立的 curated FTS 投影；不接受可切换到 `paper-working` 的检索参数。
- 当 curated 投影有未处理 outbox 时，答案保留最后可靠结果并显示索引更新提示与时间戳。
- 回答展示所用 Summary 或已确认知识，并区分作者主张、用户确认观点与 Agent 新推断。
- 用户可以沿回答来源进入对应 Paper Summary 或知识节点。
- 数据层级、索引层级和向下检索流程完成专项设计前，不实现自动下钻。
- 用户可把高价值回答送入新的 Takeaway/Insight 候选流程；仍需一键确认后才进入长期知识。

### FR-12 自动发现

- Discovery Source 支持实验室/机构、作者、arXiv 分类、关键词、Topic、Concept 和 Question。
- 定时任务获取候选论文，统一身份、去重、排序并生成推荐理由。
- 候选排序考虑来源权重、主题匹配、新颖性、与现有图谱距离及用户反馈。
- 推荐默认进入 Discovery Inbox；是否支持可信规则下的自动导入是开放决策。
- Interest Profile 应可查看、编辑和停用，不允许成为不可解释的隐藏画像。

## 8. 信息架构与领域模型

v1 的完整数据契约、术语、生命周期、不变量、存储权威性、审核边界、删除策略和
索引可见性以 [`docs/data-model.md`](data-model.md) 为准。领域统一语言见
[`CONTEXT.md`](../CONTEXT.md)。

PRD 只保留产品层约束：Paper 是跨 arXiv/DOI/正式发表版本的稳定身份；所有被使用的
内容按不可变版本保存；Conversation 是过程记录；Takeaway 是单篇 Paper 下的已确认
结论；Insight/Concept/Topic/Question/Synthesis 共享 KnowledgeNode 生命周期；来源链与
语义关系严格分离；入口 Agent 的 v1 索引仅包含 active Summary 与已确认知识。

## 9. 关键交互

### 9.1 导入

1. 用户粘贴 arXiv URL。
2. 系统立即返回已识别的论文身份或重复项。
3. 用户进入 Paper 页面查看实时处理阶段。
4. PDF 解析后并行启动 Summary 和 GitHub 仓库发现/下载/索引。
5. Summary Ready 后通知用户并开放 Summary 阅读、可选 PDF 对照和对话。
6. 代码任务可以晚于 Summary 完成，不阻塞基础阅读；代码就绪后自动加入该 Paper 的
   Agent 可用 context，并显示所固定的仓库版本。

### 9.2 Summary/PDF 对照

- 左栏按结构展示 Summary，每个关键陈述显示证据标记。
- 点击证据标记时，右栏滚动并高亮对应 PDF 区域。
- 从 PDF 选择文本后，可执行“解释”“加入问题”“用此内容提问”或“保存批注”。
- Agent 回答中的论文引用复用相同定位交互。

### 9.3 讨论沉淀

- 原始会话自动保存。
- Agent 在合适时机主动展示非打断式 Takeaway/Insight 候选。
- 候选预览其目标类型、内容、来源和将更新的关系。
- 用户一键确认后写入知识事实源并增量更新入口 Agent 的索引；拒绝不改动知识层。

### 9.4 本地访问

- Web 服务、任务执行、原始材料和知识文件均位于 Mac mini。
- 笔记本通过 Mac mini 的 Tailscale Serve 私有 HTTPS URL 访问浏览器 UI，不持有事实源副本。
- 应用只监听 `127.0.0.1`，不得自动退回 `0.0.0.0` 或直接绑定普通 LAN/Tailscale 接口。
- Tailscale Serve 将 tailnet 内的 HTTPS 请求代理到 loopback 服务；使用 tailnet ACL 限制可访问设备，明确不启用 Funnel。

### 9.5 全局问答

- MVP 检索 Paper Summary 和已确认长期知识。
- 回答主体之外展示“使用了哪些 Summary/知识”和“没有覆盖什么”。
- 用户可沿引用进入 Summary 或对应知识节点。
- 高价值回答形成 Takeaway/Insight 候选，经一键确认后进入长期知识。
- PDF、完整历史消息和代码的下钻检索明确延后，不在此阶段假定路由策略。

## 10. 自动化与人工审核边界（提案）

| 操作 | 默认策略 | 原因 |
|---|---|---|
| arXiv 元数据/PDF 获取 | 自动 | 可重复、低解释风险 |
| PDF 解析与 Summary | 自动并保留版本 | 派生内容可重建和核验 |
| 显式参考文献 `cites` | 自动确认 | 关系来自原文结构 |
| 论文明确链接的 GitHub 仓库 | 自动克隆 | 来源明确且可追溯 |
| 搜索推断的 GitHub 仓库 | 用户确认后克隆 | 错配会污染代码问答 |
| `extends`/`contradicts` 等语义边 | 生成候选，默认待确认 | 属于解释性判断 |
| 会话原文保存与索引 | 自动 | 是用户历史，但需隐私控制 |
| Agent 建议的 Takeaway/Insight | 一键确认后写入 | 应表达用户认可的长期知识 |
| 新论文发现 | 自动形成候选 | 不应无上限下载和总结 |
| 候选论文完整导入 | 默认用户确认 | 控制噪声、存储与模型成本 |

## 11. 非功能需求

### 11.1 可追溯与正确性

- 对有事实含义的 Summary 字段和 Agent 回答统计证据覆盖率。
- 引用定位在对应 Artifact 版本上必须稳定，Artifact 更新时不得静默漂移。
- 所有模型产出保留生成配置和输入版本，以便解释和重建。

### 11.2 性能（初始目标，待真实数据校准）

- 粘贴 arXiv 链接后 2 秒内返回身份识别和任务状态。
- 常规论文的可读解析结果目标在 2 分钟内可用，完整 Summary 目标在 5 分钟内可用。
- 已建立索引的全局查询，首个答案反馈目标在 5 秒内出现。
- PDF 页面切换和证据跳转不应被后台模型任务阻塞。

### 11.3 可靠性

- 所有长任务幂等、可重试且可观察。
- 单个解析器、模型或外部 API 失败不得损坏已有知识。
- 派生索引删除后应能从事实源完整重建。
- Markdown/SQLite 跨存储写入必须通过可恢复的意图状态机；恢复只能在字节级 hash
  证明没有覆盖外部编辑时自动继续，否则保存文件并创建待确认 Proposal。
- Git 是最终一致的本地历史/备份，不是知识修订的身份来源；一次恢复提交可包含多个修订。

### 11.4 隐私与安全

- 明确哪些内容发送给外部模型或 API，并允许未来按数据类型选择本地处理。
- API key、登录凭证和私有仓库 token 不进入知识库或日志。
- 代码仓库默认只读，不自动执行仓库代码或安装依赖。
- 论文与仓库文本一律按不可信数据处理；Codex 任务只读取应用提供的最小上下文，忽略
  材料中的指令，不加载用户 MCP/配置/凭证，输出须经 schema 与 Evidence Anchor 校验。
- 删除会话、论文或索引时明确事实源和派生副本的影响范围。
- 应用服务只监听 loopback；测试需证明它仅能经授权的 Tailscale Serve 入口访问，普通 LAN 地址和公网接口不可访问。

### 11.5 成本与配额

- 按论文和任务记录下载、解析、模型 token、embedding 和存储成本。
- Discovery 默认只处理元数据；完整下载、解析和 Summary 在导入后执行。
- 支持按任务设置模型质量档位和预算上限，具体策略待确认。

### 11.6 版权与合规

- 只获取用户有权访问的材料，不绕过付费墙或访问控制。
- PDF 是否提交 Git、是否同步到云端由用户明确配置；默认本地且不提交 Git。
- 对外展示或导出时避免复制超出合理引用范围的原文。

## 12. 成功指标

### 激活

- 用户从粘贴 arXiv 链接到首次打开可核验 Summary 的完成率。
- 首篇论文完成一次带证据的问答或批注的比例。

### 效率

- 从提交链接到 Summary Ready 的中位时间。
- 点击 Summary 引用成功定位原文的比例。
- 用户找到历史观点所需的平均交互次数。

### 质量

- Summary 重要陈述的有效 Evidence Anchor 覆盖率。
- Agent 引用支持其对应陈述的抽样正确率。
- 代码仓库匹配的确认准确率。
- 重复 Paper 和重复 Concept 的发生率。

### 知识积累

- 每篇已深入讨论的论文产生的已确认 Insight/Relation 数量。
- 全局问答中使用历史讨论或结构化知识并被用户保留的比例。
- 被新证据成功标记为需复审的旧 Synthesis 数量。

### 发现

- 候选论文被“导入”或“稍后阅读”的接受率。
- 推荐理由被用户认为相关的比例。
- 重复提醒和主动忽略后的再次误推荐率。

## 13. MVP 与阶段建议

### Phase 1：可信的单篇论文闭环

- arXiv 链接导入、去重和异步状态。
- PDF 保存、结构化文本解析和 Evidence Anchor。
- 按 `paper-reading` Skill 生成带引用的详细中文 Paper Summary，并保存版本信息。
- 默认 Summary 阅读页、可选 Summary/PDF 分栏和证据跳转。
- Paper-scoped 对话、历史保存和引用展示。
- 自动发现并克隆已确认的 GitHub 仓库，固定 commit，建立只读代码索引，使其可用于对话。
- 手动确认 Summary/讨论中的 Takeaway 与 Insight，并写入 Markdown 知识结构。
- 一个最小入口 Agent，可检索 Paper Summary、已确认 Takeaway/Insight 及其来源。
- 入口 Agent 不检索 PDF 原文、完整历史对话或代码；这些内容仅在 Paper-scoped Agent 中可用。
- 基础全文/向量检索及可重建索引；完整图谱和 Wiki 不作为 Phase 1 验收前置条件。

### Phase 2：跨论文知识与全局 Agent

- 显式引用图谱和可审核的语义关系。
- Concept、Topic、Question、Synthesis 的自动候选与更新工作流。
- 在数据层级专项设计完成后，再定义入口 Agent 的分层检索和检索轨迹。
- Wiki 导航、图谱浏览、知识质量检查。

### Phase 3：主动发现与持续演化

- 实验室、作者、分类、关键词和 Topic Watch。
- 可解释 Interest Profile、候选排序和反馈学习。
- 新证据对旧知识的影响分析和复审提醒。
- 在预算、隐私规则内可配置的自动导入策略。

Phase 1 的范围已经确认以单篇论文深读闭环为中心；Phase 2 和 Phase 3 的内部顺序仍可调整。

## 14. Implementation Decisions

以下是根据当前需求和仓库原则已经能够确定的实现决策：

- 领域上拆分为 Acquisition、Document Processing、Paper Workspace、Conversation、
  Knowledge、Retrieval、Discovery 和 Code Intelligence 八个可替换模块。
- Markdown/YAML 保存需要长期维护和人工编辑的知识事实；对象存储保存 PDF 和多媒体；
  关系、全文、向量和排序索引均为派生数据。
- 所有派生内容都带来源 Artifact 版本和生成版本，不做无法追溯的原地覆盖。
- 处理过程使用异步、幂等的状态机；UI 不等待完整流水线结束才创建 Paper。
- Evidence Anchor 是 Summary、对话引用、图谱关系和综合共享的核心接口。
- Conversation 原文与提炼后的 Insight 分开保存；检索可使用两者，但展示时标明层级。
- 图谱边是一等对象，不只是两个节点间的字符串；它包含证据和审核状态。
- 发现系统先产生 CandidatePaper，候选与已导入 Paper 是不同生命周期。
- 模型、PDF 解析器、embedding、代码索引器和发现源使用 Adapter 接口，避免绑定单一供应商。
- 所有 AI 任务由 Mac mini 上的 Codex CLI 执行。应用层负责准备有边界的任务上下文、
  调用 CLI、捕获结构化结果、记录运行状态并提交知识变更供审核。
- `paper-reading` Skill 纳入仓库版本管理。Summary 必须记录所用 Skill 版本，使旧 Summary
  可以解释、比较或按新版本重建。
- 首期是单用户、本地优先架构；浏览器从可私下连通 Mac mini 的笔记本访问，不提供公网服务。
- Web 服务绑定 Mac mini 的 loopback 地址，笔记本通过 Tailscale Serve 私有 HTTPS URL 访问；不得直接绑定所有接口或启用 Funnel。
- PDF、代码和知识事实源只保存在 Mac mini；派生索引与事实源分离并可重建。
- 云端模型数据边界已确认允许发送论文、代码、对话和个人知识，但仍需避免日志泄露凭证。
- SSE 每 20 秒发送心跳；以可重放的事件 ID 支持 `Last-Event-ID` 恢复。断流不代表
  Proposal 已确认，也不推进任何知识写入状态。

## 15. Testing Decisions

### 15.1 最高层测试接缝

首选一条产品级 Paper Lifecycle 接缝作为核心验收：

> 给定一个固定 arXiv 链接和一个明确关联官方 GitHub 仓库的测试样本，提交链接后，
> 系统只产生一个 Paper；自动下载 PDF，并按 `paper-reading` Skill 生成可长期访问、关键
> 结论可定位原文的中文技术 Summary。用户打开 Paper 时先看到 Summary，可选打开 PDF
> 对照。系统并行发现并克隆固定 commit 的 GitHub 仓库，完成只读索引。用户从 Summary
> 发起对话时，Agent 能以 Paper、Summary 和该代码版本为 context 给出带证据的回答。
> 用户确认一个 Takeaway 或 Insight 后，它被写入长期知识，并能从入口 Agent 检索到。
> 同一服务可由已授权笔记本通过 Tailscale Serve 私有 HTTPS URL 打开，但不能从普通 LAN 地址或公网访问。

这条接缝覆盖采集、解析、Summary、对话、知识写入和检索的主闭环，同时只验证外部
可观察行为，不绑定具体队列、数据库或模型实现。

### 15.2 必要的契约与性质测试

- arXiv/DOI/标题归一化对于同一 Paper 幂等。
- 任务重复投递和失败重试不会生成重复实体或丢失已完成 Artifact。
- Evidence Anchor 在固定 PDF/代码版本上可稳定解析到同一位置。
- Markdown 知识可以全量重建图、全文和向量索引，重建前后查询语义等价。
- curated FTS 全量重建与 outbox 增量维护的结果一致；工作语料中的 sentinel 文本永不出现在
  入口 Agent 的检索上下文或答案中。
- 用户编辑区在 Summary、Topic 或索引重建后不丢失。
- 在 `staged`、`renamed`、`metadata-committed` 边界中断后，写入恢复要么无重复地完成，
  要么保留外部内容并创建非激活的 reconciliation Proposal。
- 所有解释性 Relation 在未确认前不会被当成已验证事实回答。
- 检索回答引用的 Artifact 与生成时使用的版本一致。
- Discovery 对来自多个来源的同一论文只生成一个 CandidatePaper。
- Summary 的章节结构、条件式训练/推理章节和分析深度符合所记录版本的
  `paper-reading` Skill。
- GitHub 不存在或下载失败时 Summary 仍可 Ready；代码状态和错误可见且可单独重试。
- 论文明确提供的 GitHub 链接会自动克隆；搜索推断的仓库在确认前不会产生本地 clone。
- 已确认 Takeaway/Insight 可以被入口 Agent 检索，未确认候选不得作为用户认可观点回答。
- MVP 入口 Agent 的检索结果不会来自 PDF 原文、完整历史消息或代码索引。
- 显式 arXiv `vN` URL 在存在更高版本时仍导入 `vN`；裸 ID 在导入后冻结，打开论文时才
  创建新版本的待确认更新 Proposal。
- Tailscale Serve 下的 SSE 心跳、断线恢复与半途断流均不丢失或推断用户确认。
- 应用监听地址严格限制为 loopback；Tailscale Serve 是唯一远程入口，普通 LAN 与公网均不可访问。

### 15.3 质量评估集

- 维护一组包含双栏、公式、表格、图片和附录的固定公开论文样本。
- 维护人工标注的问题、答案、证据区域和已知冲突，用于回归评估检索和引用质量。
- 模型输出不做脆弱的逐字匹配；评估结构完整性、证据支持和关键事实是否正确。

## 16. Out of Scope（首期）

- 多用户协作、权限系统、公开知识库和社交功能。
- iOS/Android 原生客户端与离线移动阅读。
- 自动执行或训练论文代码、GPU 作业编排和实验复现平台。
- 对所有学术数据库、出版社和付费内容的统一采集。
- Zotero/Obsidian/Notion 双向同步；可以后续以 Connector 形式增加。
- 引文格式管理、投稿排版和完整 Reference Manager 功能。
- 无人审核地将所有模型推断直接写入长期知识层。
- 让知识图谱成为唯一存储；它始终是可追溯事实的结构化视图。

## 17. 开放决策

以下问题会实质影响 MVP、部署方式或数据模型，需要在进入技术设计前确认：

1. **Codex CLI 调度**：首期是否只允许同时处理/对话一篇 Paper，还是必须支持多个 Codex
   任务并行？这会影响队列、资源限制和知识文件写入冲突处理。
2. **Tailscale 内认证**：只依赖 tailnet ACL，还是仍需一个简单的应用登录/访问令牌？
3. **代码深度**：首期已确认只读代码 context；后续是否明确需要沙箱执行和实验复现？
4. **历史对话隐私**：是否需要“保存但不参与全局检索”的会话或消息？
5. **现有资产迁移**：是否已有 Zotero、Obsidian、PDF 文件夹或聊天记录需要首期导入？
6. **成本与速度**：详细技术精读更偏向最高质量，还是需要为单篇论文设置时间/token 预算？
7. **数据与检索层级**：在设计入口 Agent 下钻前，需要先确认 Artifact、Summary、Conversation、
   Takeaway、Insight 与结构化知识之间的完整层级、生命周期和权威性。

## 18. Further Notes

- “自动发现”与“知识库问答”共享 Interest、Topic 和 Retrieval 能力，但候选论文不应在
  用户确认前进入正式知识图谱，否则推荐噪声会变成知识噪声。
- 完整聊天记录值得保留，但它与 Summary、Takeaway、Insight 的权威性和索引层级尚未
  最终确定；入口 Agent 是否以及如何下钻到原始消息留待数据层级专项设计。
- 论文间“传承、借鉴、同一路线”不是客观元数据。它们需要以可解释 Relation 的形式
  存储证据和置信度，并允许用户纠正。
- GitHub 仓库会变化。任何依赖代码的回答都需要固定 commit SHA，否则未来无法复现
  当时的依据。
- 不同 Paper 的 Takeaway 可能对同一个 Insight 形成 `supports`、`challenges` 或明确冲突。
  后续自动归纳应主动识别并呈现这些关系，而不是将冲突平均成一个模糊结论。这是重要的
  后续能力，但关系判定、聚类和审核交互不在当前数据层级访谈中展开。
